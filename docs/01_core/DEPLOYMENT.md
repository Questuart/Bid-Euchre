# Browser Game Deployment

**Status:** V1 deployment guide
**Last updated:** 2026-03-24

---

## 1. Overview

The browser game is a FastAPI application served by uvicorn, with Jinja2
server-rendered templates and HTMX for interactive updates. It supports SQLite
for local development and Postgres for production.

**Key files:**

| File | Purpose |
|------|---------|
| `Dockerfile` | Production Docker image |
| `.dockerignore` | Keeps image lean (~200 MB vs ~1.5 GB) |
| `render.yaml` | Render Blueprint (web service + Postgres) |
| `.env.example` | Environment variable contract |
| `web/config.py` | `HostedPlayConfig` dataclass |

## 2. Deploy to Render

Render is the default hosting target. The `render.yaml` Blueprint defines a
web service (Docker runtime) plus a managed Postgres database.

### Steps

1. Push `render.yaml` and `Dockerfile` to `main` (already merged).
2. Create a Render account at <https://render.com>.
3. Connect the GitHub repo (`Questuart/Bid-Euchre`).
4. Select **Blueprint** and Render auto-discovers `render.yaml`.
5. Click **Apply** — Render provisions the web service and Postgres database.
6. Wait for the first deploy to complete (~3-5 minutes).
7. Visit the assigned URL (e.g., `https://bideuchre-web.onrender.com`).

### What the Blueprint provides

- **Web service:** Docker build from `Dockerfile`, auto-deploy on main pushes.
- **Postgres:** Managed free-tier instance; `DATABASE_URL` injected automatically.
- **SECRET_KEY:** Auto-generated by Render (`generateValue: true`).
- **Health check:** `GET /` (landing page returns 200).

### Post-deploy verification

```bash
# Liveness
curl -s https://<render-url>/health
# → {"status":"ok"}

# Readiness (DB connectivity)
curl -s https://<render-url>/ready
# → {"status":"ready"}
```

## 3. Environment Variables

All configuration is via environment variables. See `.env.example` for the
full contract with defaults. The authoritative source is `web/config.py`
(`HostedPlayConfig.from_env()`).

| Variable | Required in prod | Default | Purpose |
|----------|-----------------|---------|---------|
| `DATABASE_URL` | Yes | `sqlite:///hosted_play.db` | SQLAlchemy connection string |
| `SECRET_KEY` | Yes | Random per-process (dev) | Cookie/session signing |
| `ALLOWED_ORIGINS` | No | `*` | Comma-separated CORS allowlist |
| `APP_URL` | No | `http://localhost:8000` | Public base URL for share links |
| `DEFAULT_MODEL_ID` | No | `heuristic` | AI bidding model |
| `MODELS_DIR` | No | None | Directory for model artifacts |
| `HYBRID_OLSA_ARTIFACT` | No | None | Path to hybrid-OLSA artifact |
| `DEBUG` | No | `false` | Enable debug mode (`1`/`true`/`yes`) |
| `PORT` | No | `8000` | Server bind port (Render sets this) |

**Production requirements:**
- `DATABASE_URL` must point to Postgres (Render injects this from the managed DB).
- `SECRET_KEY` must be set to a stable value (Render auto-generates it).
- `APP_URL` should be set to the public Render URL for correct share links.

## 4. Run Locally with Docker

### Build

```bash
docker build -t bideuchre-web .
```

### Run (SQLite, dev mode)

```bash
docker run --rm -p 8000:8000 \
  -e DATABASE_URL=sqlite:///hosted_play.db \
  -e SECRET_KEY=dev-local-test \
  bideuchre-web
```

Open <http://localhost:8000> — the landing page should load.

### Run with local Postgres

```bash
# Start Postgres (example with Docker)
docker run --rm -d --name pg \
  -e POSTGRES_DB=bideuchre \
  -e POSTGRES_USER=bideuchre \
  -e POSTGRES_PASSWORD=devpass \
  -p 5432:5432 \
  postgres:16

# Run the app against it
docker run --rm -p 8000:8000 \
  -e DATABASE_URL=postgresql://bideuchre:devpass@host.docker.internal:5432/bideuchre \
  -e SECRET_KEY=dev-local-test \
  bideuchre-web
```

### Run without Docker (development)

```bash
cp .env.example .env
# Edit .env as needed
uv sync --extra hosted
uv run uvicorn web.app:create_app --factory --reload --port 8000
```

## 5. Create a Match and Share a Link

1. Open the landing page (`/`).
2. Enter a nickname and click **Create Match**.
3. The app generates a UUID-based private link (e.g., `/match/<uuid>`).
4. Share the link — anyone with the link can spectate or (in V1) the link
   owner plays as seat 0.
5. Bid when it's your turn, play cards by clicking them.
6. The match continues until one team reaches ±52 points.

See `docs/01_core/HOSTED_PLAY_RULES.md` for the full match rules.

## 6. Known Limitations (V1)

| Limitation | Notes |
|------------|-------|
| Single human player | Seat 0 only; seats 1-3 are AI. Multiplayer is post-V1. |
| No authentication | Access is via UUID link only. No login, no accounts. |
| Permissive CORS | `ALLOWED_ORIGINS=*` in dev; should be tightened for production. |
| Free-tier cold starts | Render free-tier spins down after inactivity; first request may take ~30s. |
| No model hot-swap | AI model is fixed per match at creation time. |
| SQLite in Docker | Local Docker uses SQLite by default (single-process safe). Use Postgres for any multi-worker deployment. |

## 7. Architecture Notes

```
Browser ──HTMX──▶ FastAPI (uvicorn)
                      │
                      ├─ Jinja2 templates (server-rendered HTML)
                      ├─ SQLAlchemy (SQLite or Postgres)
                      ├─ AIManager (loads approved models on startup)
                      └─ Decision logger (persists every bid/play)
```

- **No client-side JavaScript framework** — HTMX handles all interactivity.
- **Server-rendered partials** — each action returns an HTML fragment that
  HTMX swaps into the DOM.
- **Stateless server** — all game state is in the database. Browser refresh
  resumes from persisted state.
- **Decision logging** — every human and AI action is persisted for later
  training data export (see Phase 4 data pipeline).

## 8. Monitoring

| Endpoint | Purpose | Expected response |
|----------|---------|-------------------|
| `GET /health` | Liveness probe | `{"status": "ok"}` (always 200) |
| `GET /ready` | Readiness probe | `{"status": "ready"}` (200) or `{"status": "unavailable"}` (503) |
| `GET /` | Landing page | HTML 200 (used as Render health check) |
